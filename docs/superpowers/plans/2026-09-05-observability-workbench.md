# 灵机可观测工作台实施计划（2026-09-05，主人需求列表落地）

> 定位：主人只验证、不操作。UI 是看灵机工作过程的窗口，不是知识库管理工具。

## 硬规则（贯穿全部任务）

1. 每个专业术语紧跟大白话解释（是什么/没它会怎样/怎么修）。
2. 需要主人决定的事项主动弹窗，不允许等主人翻页面发现。
3. 向量/RAG/Embedding 是 AI 内部设施，只在"服务状态"透明展示，不占主人界面。
4. 新验收门槛：任何新功能必须同时具备 UI 入口、`docs/MODULES/FUNCTION_MAP.md` 功能地图条目、
   工作记录可追踪，三者缺一不算验收完成（验收同步脚本检查）。
5. 不新增第二套数据库/队列/状态源——全部页面从现有 StateDB events、Work Fact、ScanRun、
   extraction jobs、结构化版本链投影生成。
6. 只读安全边界不变：不读真实凭证、不写入来源 AI、零副作用。

## 三面板信息架构

- 面板一「原始数据」= 需求 3 信息流 + 来源授权管理
- 面板二「灵机整理」= 保留/覆盖明细（2.3）+ 提炼记忆卡 + 进入永久记忆的确认入口
- 面板三「永久记忆」= 需求 4（当前全部永久记忆 + 元数据 + 分类）
- 菜单顺序：总览/工作记录/信息流(原始数据)/永久记忆/时间线/…/功能地图/系统状态/设置；高级诊断收纳。

## P0 批（"看懂灵机一天"最小闭环）

### Task A：工作记录页（2.1–2.4）
- 后端投影 API（新 `src/control/observability_api.py`，只读投影、白名单字段、复用认证）：
  - `GET /api/observability/tasks`：automatic_memory_scans + work items 按时间倒序；
    每行 = 时间/任务名/状态/结果摘要（真实 queued/failed/reused/duplicates 计数）。
  - `GET /api/observability/tasks/{scan_id}/steps`：九步流水（原始获取→解析→去重→有效性筛选→
    信息提取→记忆判断→记忆更新→时间线→向量化）每步真实计数；缺失显示"尚未获得"，不编造。
  - `GET /api/observability/tasks/{scan_id}/items`：逐条明细，被保留/被忽略/被覆盖三态，
    被覆盖带 superseded_by 版本链对照；失败条目主人可读原因分类映射（不暴露堆栈/路径/内部 ID）。
- 前端：菜单第二位"工作记录"页：任务列表 → 详情步骤表 → 明细展开。
- e2e：fixture 投影数据 + 列表/步骤/明细/失败分类断言。

### Task B：变更账本（6.1–6.2）
- `GET /api/observability/changes`：StateDB events + 结构化版本链按时间排列（动作类型/对象/时间）。
- 每条可展开：修改前→修改后→来源→系统为什么这么做；缺来源显示"尚未获得"。
- 前端"变更账本"页（高级诊断收纳后仍在主菜单）。

### Task C：信息流（3.1）
- `GET /api/observability/feed`：全部 scan items 一行一条 + 真实管线状态
  （未处理/处理中/已保留/已提取/已合并/已忽略/已更新/失败；queued/reused 永不显示为已导入）。
- 前端"原始数据"页上半区为信息流（状态/时间筛选 P1 跟进）。

### Task D：首页实时工作流（1.2）
- 首页"正在做什么"升级为分步流水：当前任务九步 + 各步数量 + 完成百分比；无任务显示"空闲+上次结果"。
- 数据源复用 Task A steps API（当前进行中的 scan）。
